# VISION

## 1. Что мы строим

Локальная веб-консоль для агента `omp`.

Пользователь работает с настоящим `omp`, запущенным на его машине, но не через
терминал, а через браузер: несколько сессий, живой стриминг, история и ветвление,
файлы, git, уведомления на другие устройства. В перспективе — рабочее место,
которое совмещает возможности редактора, AI-агента и git-клиента.

omp-web — не агент и не замена `omp`. Это **мост**: сервер запускает настоящий
`omp`, говорит с ним по его RPC-протоколу и отдаёт клиенту один предсказуемый
HTTP/SSE-контракт.

## 2. Принципы

1. **`omp` остаётся настоящим.** Мы не встраиваем SDK, не эмулируем движок, не
   переписываем инструменты, модели, компакцию или субагентов. Всё, что делает
   агент, делает бинарник `omp`.
2. **Клиент-сервер.** Клиент — только UI. Он вызывает сервер и рисует ответ.
   Сервер выполняет всю работу: процессы, файлы, состояние, сеть, политики.
3. **Framework-agnostic логика.** Домен не знает про React, DOM, Bun, HTTP и
   файловую систему. Слои явные, каждый тестируется отдельно.
4. **Предсказуемость важнее скорости разработки.** Один источник истины, тотальные
   парсеры, стабильные коды ошибок, аддитивные изменения контракта.
5. **Нативный Bun внизу.** Bun-API там, где он есть; `node:*` там, где это
   единственный API; никаких собственных имитаций чужих интерфейсов.

## 3. Слои

| Слой | Владеет | Не знает про |
|---|---|---|
| `core/` | домен: типы, парсеры кадров, reducer, интенты, история, поиск, маршрутизация уведомлений, компакция, субагенты | I/O, таймеры, `fetch`, DOM, Bun, файлы, HTTP |
| `lib/` | хост: процессы `omp`, RPC-транспорт, файлы сессий, конфиги, git, файлы проекта, медиа, уведомления, STT, обновления | HTTP-формы, рендеринг |
| `server/` | контракт: маршруты, валидация, коды ошибок, SSE, безопасность | бизнес-правила, формат файлов `omp` |
| `contract/` | сгенерированный `open-api.yaml` и описание SSE-событий | исполняемая логика |
| `web/` | UI: рендеринг, ввод, optimistic UI | прямые вызовы `lib`/`server`, файловую систему, процессы |

Правило размещения: доменное правило → `core`; политика ОС/рантайма → `lib`;
форма транспорта → `server`. Если правило нужно и серверу, и UI — оно живёт в
`core`, а не дублируется на клиенте.

`web/` — классический фронтенд: только HTTP-вызовы, сгенерированные из OpenAPI
типы и клиент. Импорт `core/`, `lib/` или `server/` из `web/` запрещён.

## 4. Кто владеет состоянием

Сервер авторитетен. Это прямое следствие принципа «сервер выполняет всю работу».

- Сервер держит актуальное состояние сессии: транскрипт, run, очередь, вью,
  ветвление. Он получает кадры от `omp`, прогоняет их через `core` и отдаёт
  клиенту **снимки и дельты**, а не сырой поток.
- Клиент отправляет **интенты** (`prompt`, `steer`, `fork`, `compact`, …) и
  рисует снимок. Локальный reducer допустим только для optimistic UI; источник
  истины — сервер.
- Сырые кадры остаются debug-каналом, но не публичным контрактом UI.

Следствия:

- несколько вкладок и устройств видят одно состояние без клиентской синхронизации;
- переподключение — это повторный снимок, а не повторное проигрывание кадров;
- `core` — мозг сервера, а не SDK без потребителя;
- авторитетное состояние подключено: `AgentSessionWrapper` владеет одним
  `core/machine.ts` (`lib/session-authority.ts`), отдаёт снимок
  (`GET /api/agent/sessions/[id]/state`, SSE `snapshot`) и интенты
  (`POST /api/agent/sessions/[id]/intent`);
- в `lib/rpc-manager.ts` остаются только lifecycle-флаги процесса
  (запуск/перезапуск, ожидание ответа, reap); разговорное состояние — в ядре;
- сырые кадры идут в SSE как debug-канал, клиентский контракт — снимки и
  дельты.

## 5. Контракт API

Домены, а не плоский список:

- `/api/agent/*` — сессии, интенты, живое состояние, host tools, субагенты,
  расширения;
- `/api/workspace/*` — файлы, индекс, git, worktrees, проекты, медиа;
- `/api/system/*` — модели, провайдеры, настройки, usage, уведомления, STT,
  skills, MCP, обновления.

Правила:

- команды — HTTP `POST`/`PATCH`/`DELETE` с JSON; события — один SSE на браузер с
  мультиплексированием каналов;
- один конверт ошибки: `{ error, code }`; коды стабильны; 4xx — ошибка входа,
  5xx — отказ хоста;
- изменения только аддитивные; ломающее изменение — новая версия;
- все парсеры на границе тотальны: мусор → `null`/400, не исключение;
- UI не импортирует `lib` и `core` напрямую, только HTTP-контракт.

**OpenAPI (Swagger) — генерируемый артефакт.** Схемы запросов и ответов живут в
коде рядом с маршрутами и служат единственным источником: по ним валидируется
вход и из **актуального бэкенда** собирается `contract/open-api.yaml`. Файл
коммитится в git. CI перегенерирует спеку и падает на непустом diff — так
контракт и код не расходятся.

Клиент не получает типы от сервера: он строит свою типизацию из `open-api.yaml`
своим генератором. Сервер отвечает только за корректную спеку. Формат артефакта
не принципиален: YAML выбран ради читаемого diff, клиентские генераторы
принимают и YAML, и JSON.

Требования к генератору: детерминированный порядок ключей и путей, без
временных меток, стабильное форматирование. Иначе diff спеки шумит на каждом
коммите. Для просмотра в dev-режиме спека может отдаваться через Swagger UI; в
прод этот экран не включается.

SSE в OpenAPI описывается плохо. Поток и его конверты живут отдельным
документом `contract/events.md` и покрываются контрактными тестами.

Плоские маршруты (`/api/files`, `/api/git`, `/api/sessions`) переименованы в
домены `/api/agent|workspace|system` в M1, до появления UI. После появления UI —
только аддитивно.

### Чего не хватает для редактора

| Нужно UI | Сейчас |
|---|---|
| сохранение/переименование/удаление файла | да: `PUT`/`PATCH`/`DELETE /api/workspace/files/[...path]` |
| stage/commit/branch/checkout | да: `/api/workspace/git/{stage,unstage,commit,branches,checkout}` |
| живые изменения файлов проекта | да: SSE-канал `workspace` (`workspace-changed`) |
| терминал | да: WebSocket `/api/workspace/terminal` (PTY, вне `omp`) |
| LSP/диагностика | да: `/api/workspace/lsp/{documents,diagnostics}`, SSE-канал `lsp` |

LSP и inline-правки осознанно оставались вне M1–M2 и появились в M4, не меняя
агентские маршруты.

## 6. Механики

| Механика | Правило |
|---|---|
| Процесс | один настоящий `omp --mode rpc-ui` на живую сессию; spawn по требованию; reap после отключения последнего клиента; лимит и журнал — в `lib/` |
| Транспорт | NDJSON по stdin/stdout; кадр готовности; коррелированные ответы; события вперемешку; stderr-хвост для диагностики |
| Долговечность | история — JSONL-файлы `omp`; live-слой — кадры; журнал resume для прерванных запусков; один писатель файла — `omp` |
| Версии | новый `omp` не роняет старый сервер и старого клиента: неизвестные кадры игнорируются |
| События | один SSE на браузер; каналы session/running/notifications/file/host-tools; heartbeat; backpressure со схлопыванием `message_update` |
| Host tools | агент вызывает хост (`open_url`, `notify`, `open_file`); вызов адресуется подключению, имеет TTL и авторизацию |
| Файлы | доступ в рамках разрешённых корней и сессии; symlink-safe open; range-запросы |
| Уведомления | push-подписки, presence/devices, маршрутизация в сфокусированную вкладку |
| Skills | установка/обновление через `bun x`; lock, диагностика |
| Usage | SQLite (`bun:sqlite`), агрегаты по файлам сессий |
| Медиа | content-addressed кеш; превью через `sharp` |
| STT | очередь задач, аудио-blob, TTL результата |
| Обновления | self-update omp-web и `omp update`; блокировка при активных сессиях |
| Терминал | PTY для задач вне `omp` (dev-серверы, тесты, git); отдельный от bash-инструмента агента; двунаправленный канал (WebSocket), не SSE; только при пройденном гейте |

## 7. Безопасность и границы

- один пользователь навсегда: без аккаунтов, ролей и multi-tenant;
- по умолчанию сервер слушает loopback;
- любой bind не на loopback требует явного гейта доступа — reverse proxy с
  корпоративной аутентификацией или общий секрет. Сервер не должен стартовать
  открытым без гейта;
- cross-origin запросы с телом отклоняются;
- файловый доступ авторизуется по сессии и разрешённым корням, а не по «путь
  пришёл от клиента»;
- файлы сессий принадлежат `omp`; сервер читает их и не переписывает, кроме
  явного flow правки через расширение `omp`;
- один писатель файла сессии — `omp`;
- PTY — это полноценный shell от имени пользователя сервера. Он доступен только
  при пройденном гейте и не даёт дополнительной песочницы; это осознанное
  решение, а не недосмотр.

## 8. UI

UI живёт в этом репозитории в `web/`, но остаётся классическим фронтендом:
общается с сервером только через HTTP по OpenAPI-контракту. Импорт `core/`,
`lib/` или `server/` из `web/` запрещён; общий код — только сгенерированный
клиент и типы.

- визуальные ориентиры — Cursor и DeepSeek harness: плотный интерфейс, стриминг
  на первом плане, минимум декоративного хрома, код и текст важнее панелей;
- базовая тема — светлая; тёмная переключается в рейле и хранится в
  `omp.theme.v1`. Палитра живёт в токенах `web/src/styles/tokens.css`, поэтому
  тема не меняет компоненты. В дальнейшем тема сможет задавать и layout
  (Cursor-подобный или Claude Code/DSH-подобный), а не только цвета;
- типографика: sans для интерфейса, mono только для кода, путей, diff и
  терминала. Редактор — Monaco;
- поведение — keyboard-first, без модальных «мастеров», с предсказуемыми
  состояниями загрузки и ошибок;
- редактор — Monaco; дерево файлов и git-панель — свои компоненты в стиле
  VS Code;
- **факт:** официально переиспользуется только Monaco. Explorer, git-панель и
  терминал VS Code не поставляются как библиотека веб-компонентов: это части
  workbench, завязанные на его внутренние сервисы (explorer/SCM/контекстные
  меню/DI), а не публичный API. Сторонние наборы (`@vscode-elements/elements`)
  не являются официальными и не дают сами панели. Поэтому explorer и git —
  собственные компоненты поверх `/api/workspace/*`, а Monaco + xterm.js —
  единственные официальные кирпичи;
- DSH — только визуальный ориентир. Его компоненты не переиспользуются, код не
  переносится;
- стек UI зафиксирован: React 19 + Vite 8 + TypeScript 7 (strict), SPA без SSR.
  Типы и HTTP-клиент — из `open-api.yaml` (`openapi-typescript` +
  `openapi-fetch`), HTTP-кэш — TanStack Query, снимки — один внешний стор на
  `useSyncExternalStore`, SSE — одно мультиплексированное соединение. Правила —
  в `AGENTS.md`, раздел «Web rules».

## 9. Этапы

«Комбайн VS Code + Cursor + omp» — северная звезда, а не объём первой версии.
Порядок: контракт → авторитетное состояние → рабочее место → UI → совмещение.

**M1. Контракт и консоль агента (этот репозиторий).** OpenAPI-спецификация и
домены `/api/agent|workspace|system`, единый конверт ошибок, удаление Next-шима
и дефектов HTTP-слоя. Авторитетное состояние сессий, интенты, живой стриминг,
история/поиск/архив, host tools, уведомления, файлы на чтение,
модели/настройки/skills/MCP/usage. Тесты на все слои, контрактные тесты.
**Статус: выполнено** (Zod 4, `contract/open-api.yaml`, `contract/events.md`,
CI `contract:check`).

**M2. Рабочее место.** Запись/переименование/удаление файлов, git
stage/commit/branch, watcher проекта, дерево и индекс. PTY для задач вне `omp`.
**Статус: выполнено** (`PUT/PATCH/DELETE /api/workspace/files`,
`/api/workspace/git/*`, SSE-канал `workspace`, `/api/workspace/index`,
WebSocket `/api/workspace/terminal` на `node-pty`).

**M3. UI в `web/`.** Консоль, Monaco, панели файлов и git. Только HTTP;
типизация клиента — из `open-api.yaml`. Визуальный ориентир из §8.
**Статус: выполнено** (React 19 + Vite 8, чат на снимках, workbench
Files/Changes/терминал, Monaco + xterm.js, Playwright e2e).

**M4. Совмещение.** Inline-правки в стиле Cursor, LSP-диагностика, multi-root,
расширения. Только после стабильных M1–M3.
**Статус: выполнено** (inline-правки через scoped-промпт в активную сессию,
LSP через `lib/lsp` + `/api/workspace/lsp/*` и SSE-канал `lsp`, multi-root в
workbench; extension-запросы `omp` обрабатываются в M3, extension host VS Code
остаётся non-goal §10).

## 10. Non-goals

- переписывать `omp`, встраивать `@oh-my-pi` SDK, эмулировать движок;
- UI-фреймворк вне `web/`; импорт серверного кода в UI;
- аккаунты и роли в приложении, multi-tenant, облачная синхронизация;
- extension host VS Code и запуск произвольных расширений;
- пиксельная копия VS Code;
- мобильные нативные приложения.

## 11. Политика Bun

- Bun-API, если он существует: `Bun.serve`, `Bun.spawn`/`spawnSync`,
  `Bun.file`/`Bun.write` (только async-пути), `Bun.Glob`, `Bun.CryptoHasher`,
  `Bun.gzipSync`/`gunzipSync`, `Bun.which`, `Bun.fileURLToPath`/
  `pathToFileURL`, `Bun.inspect`, `bun:sqlite`;
- `node:*`, если это единственный API: `path`, `os`, синхронные `fs`-чтения и
  записи, `fs`-примитивы (`lstat`, `open`, `rename`, `fsync`, `chmod`,
  `symlink`), потоковый `zlib`, `readline`;
- никаких собственных шимов чужих API;
- адаптер допустим только для политики, которой нет в Bun: таймауты и лимиты
  вывода процесса, атомарная запись, авторизация файлов, symlink-защита;
- «обратная совместимость Bun» — это реализация `node:*`, а не отдельный
  Bun-API. Удаление `node:` ради удаления префикса — не цель.

**Платформы.** Рантайм один — Bun; веб один. Различаются ОС-семантики: `.cmd` и
кавычки аргументов, регистр путей, symlink-права, PTY. Они изолируются в `lib/`
и покрываются платформенными тестами. Приоритет разработки — Windows (рабочая
машина), CI — Linux; macOS best-effort. Продуктового приоритета между ОС нет.

## 12. Решения

Принято:

1. Плоские маршруты переименованы в домены в M1, до появления UI.
2. Однопользовательский режим навсегда; loopback по умолчанию; не-loopback bind
   требует явного гейта (reverse proxy или общий секрет).
3. Рантайм и веб одинаковы на всех ОС; различаются только ОС-семантики, они
   изолированы в `lib/`. Приоритет тестов — Windows + Linux.
4. PTY нужен для задач вне `omp` (M2); LSP — дальний прицел (M4).
5. UI живёт в `web/` этого репозитория, но общается только через HTTP + OpenAPI.
6. Порядок: контракт → авторитетное состояние → workspace → UI → совмещение.
7. OpenAPI — code-first: схемы в коде, из актуального бэкенда генерируется
   `contract/open-api.yaml`, файл коммитится, CI проверяет отсутствие diff.
   Клиент строит свою типизацию по этой спеке сам.
8. DSH — только визуальный ориентир, компоненты не переиспользуются.

9. Библиотека схем — Zod 4 (`z.toJSONSchema`), генератор
   `scripts/generate-openapi.ts`, артефакт `contract/open-api.yaml`.
10. UI: React 19 + Vite 8 + TypeScript 7, SPA только по HTTP; Monaco и xterm.js
    официальные, explorer/git — свои. Клиент типизируется из `open-api.yaml`.
11. Базовая тема — светлая, тёмная доступна переключателем (`omp.theme.v1`).
    Палитра и типографика — токены; темы в перспективе задают layout
    (Cursor / Claude Code|DSH), поэтому layout не зашивается в компоненты.

Вне этой сессии: UI-фреймворк. Решение не влияет на серверный контракт и
принимается отдельно.
